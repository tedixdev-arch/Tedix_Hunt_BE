# Participant gameplay — dependency-ordered PR boundaries

Task 5C handoff only. No implementation is authorized by these future slice descriptions. Existing Master and Implementation Plans remain unchanged. Every slice reuses the same Hunt/Participant/Team, pinned snapshot/execution digest and checkpoint engine. Each row is one bounded PR unless the row explicitly says “per mechanic”; do not bundle a new engine or all 22 mechanics into one change.

Review [remaining decisions](Participant_Gameplay_Decisions.md) first. Existing content-chain, exact approval, route safety/access and publication gates remain prerequisites to live use. A controlled Solo proof has one normal checkpoint plus FinishPoint, followed by two-account Team and variable-size proofs; seven-stop Signal expansion comes later without an eighth terminal step. Minimal truthful HELP/PANIC/operations and safety requirements gate each live proof; a coding test pass does not replace those product release gates.

Independent preparatory branches may run after their own prerequisites, but live proof order remains A → B → C. Unrelated leaderboards, Passport awards, invitation platform, continuous GPS tracking, WebSockets and advanced maps are separate future scope, not invented prerequisites or silently enabled features.

Every backend implementation PR uses real authenticated Express/PostgreSQL tests where it claims runtime behavior, all current migrations plus its own, concurrency/rollback evidence and runtime Swagger consistent with actual routes. Every frontend PR distinguishes source integration from independently recorded deployed/device acceptance. No merge/deploy is part of Task 5C.
