## Inspection and reusable mechanisms

- `src/routes/participantAccess.ts` authenticates both enrollment and `/participants/me`, rejects unknown enrollment fields, normalizes optional codes, scopes responses to the token subject and disables response caching. It never calls a membership writer.
- `src/models/ParticipantAccess.ts` starts a transaction, locks the exact Hunt then the caller's membership, verifies an optional code against that same Hunt, checks lifecycle, and initializes durable checkpoint/access records against the frozen source/radius digest. Existing UUIDs, join time and evidence survive rejoin. No Team is required or assigned. All initialization rolls back on failure; no new gameplay grant is enabled.
- Exact reason for `enrollment_policy_unresolved`: a matching code and `published`/`active`/`paused` Hunt reach the explicit `!participant` branch. A caller without membership and without a code gets 404; a mismatched code gets 404; ineligible lifecycle with a matching code gets 409. A public code is metadata lookup, never admission authorization. These HTTP semantics remain unchanged.
- `HuntParticipant.enroll` previously performed an unconditional upsert keyed by `(hunt_id,user_id)`. It was used only by tests, with no authentication, invitation, capacity or lifecycle checks. It now resolves an existing identity or throws 422 `enrollment_policy_unresolved`; it never inserts or updates. Its name is retained for compatibility. It is an internal identity lookup, not an authenticated access endpoint; ParticipantAccess remains responsible for access/lifecycle. Future admission must replace this policy gate deliberately after approval. Direct SQL in tests explicitly represents historical fixtures, not an approved provisioning route or an operational workaround.
- `HuntContext.findForUser` derives contexts from actual `hunt_participants` and Hunt-scoped Supervisor assignments. Account roles, context selection, Team IDs and Hunt UUID knowledge do not create membership. Database unique/composite foreign keys already isolate membership, Teams and checkpoint access by Hunt.
- `src/domain/huntAccess.ts`, `src/routes/huntAccess.ts`, `Hunt.ensureAccessCode` and `Hunt.findByAccessCode` provide normalized random unique codes and minimal public identity/status lookup. No invitation issuance, acceptance, expiry or revocation records exist. `invitation_only` is the only access mode; selecting it generates no eligibility.
- Hunt setup stores positive capacity and validates publication readiness. Existing lifecycle actions serialize through the Hunt row; draft-only updates cannot change live capacity. There is no approved new-admission lifecycle/late-entry rule, capacity reservation rule or capacity-enforcing first-admission writer. This PR cannot certify final-seat admission races. Concurrent denied requests create zero memberships; existing-member rejoin consumes no seat, including at capacity.
- `requireAuth` verifies access-token type/signature and reloads the user; blocked/retired identities are denied. Account sign-in and refresh preserve the user ID. `POST /auth/guest` always creates a new guest identity with a one-hour token and no refresh token; its body cannot select another user. A still-valid original guest token can reconnect; a lost/expired token has no supported recovery/account-link flow. A new guest session is not a recovery credential.
- Organizer Hunt management requires Hunt-specific Organizer assignment. Supervisors have existing scoped reader permissions, not admission authority. Neither global Organizer/Admin nor Supervisor role grants Participant access. No permissions, auth, abuse budgets, publication checks or snapshot guards are broadened here.
